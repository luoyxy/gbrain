# 摄取技能#

将会议、文章、媒体、文档和对话摄取到大脑中。

> **归档规则：** 在创建任何新页面之前阅读 `skills/_brain-filing-rules.md`。

## 合约#

- 写入大脑页面的每个事实都带有内联 `[来源: ...]` 引用和日期及来源。
- 每个实体提及都会从该实体的页面创建反向链接到提到它们的页面（铁律）。
- 原始来源通过 `gbrain files upload-raw` 保留用于来源保留，带有自动大小路由。
- 状态部分用当前最佳理解重写，永远不附加。
- 实体检测在每个入站消息上触发；显著实体获得页面或更新。

> **约定：** 参见 `skills/conventions/quality.md` 了解铁律反向链接。
>
> 每次提到有大脑页面的人员或公司都必须从该
> 实体的页面创建反向链接到提到它们的页面。未链接的提及是
> 损坏的大脑。参见 `skills/_brain-filing-rules.md` 了解格式。

## 引用要求（强制性）#

写入大脑页面的每个事实都必须带有内联 `[来源: ...]` 引用。

- **用户的陈述：** `[来源: 用户, {上下文}, YYYY-MM-DD]`
- **会议数据：** `[来源: 会议 "{标题}", YYYY-MM-DD]`
- **电子邮件/消息：** `[来源: 来自 {姓名} 的电子邮件 re: {主题}, YYYY-MM-DD]`
- **网络内容：** `[来源: {发布}, {URL}, YYYY-MM-DD]`
- **社交媒体：** `[来源: X/@handle, YYYY-MM-DD](URL)`（包含链接）
- **综合：** `[来源: 编译自 {来源}]`

## 阶段#

> **路由器说明：** 此技能是路由器。对于专门的摄取，参见：idea-ingest、media-ingest、meeting-ingestion。

1. **解析来源。** 从输入中提取人员、公司、日期和事件。
2. **对于每个提到的实体：**
   - 从 gbrain 读取实体页面以检查它是否存在
   - 如果存在：更新 compiled_truth（用新信息重写状态部分，不要附加）
   - 如果是新的：检查显著性门控，然后在 gbrain 中用适当的类型和 slug 存储页面
3. **附加到时间线。** 在 gbrain 中为每个事件添加时间线条目，带有日期、摘要和来源引用。
4. **创建交叉引用链接。** 使用适当的关系类型为每个一起提到的实体对链接 gbrain 中的实体。
5. **反向链接所有实体。** 用反向链接到此后页面更新每个提到的实体的页面（铁律）。
6. **时间线合并。** 相同事件出现在所有提到的实体的时间线上。如果 Alice 在 Acme Corp 会面了 Bob，事件就会出现在 Alice 的页面、Bob 的页面和 Acme Corp 的页面上。

## 在每个消息上的实体检测#

生产智能体应该在每个入站消息上检测实体提及。这是
使大脑随时间复合的信号检测循环。

### 协议#

1. **扫描消息**以查找实体提及：人员、公司、概念、原始
   思考。在每个消息上触发（除非纯粹是操作性的，否则没有例外）。
2. **对于每个检测到的实体：**
   - `gbrain search "姓名"` —— 页面是否已存在？
   - **如果是：** 用 `gbrain get <slug>` 加载上下文。使用编译真相来
     告知你的响应。如果消息包含新信息，更新页面。
   - **如果否：** 评估显著性（参见 `skills/_brain-filing-rules.md`）。如果实体
     值得跟踪，用 `gbrain put <类型/slug>` 创建新页面并用你
     知道的内容填充。
3. **创建或更新页面后：** 同步到 gbrain：
   ```bash
   gbrain sync --no-pull --no-embed
   ```
4. **不要阻断对话。** 实体检测和丰富应该 alongside
   响应发生，而不是在它之前。用户不应该等待大脑写入
   以获得答案。

### 什么算作显著的#

- 用户与之交互或讨论的人员（不是随机提及）
- 与用户的工作或兴趣相关的公司
- 用户引用或创建的概念或框架
- 用户自己的原始思考（想法、论点、观察）-- 最高价值

参见 `skills/_brain-filing-rules.md` 了解完整的显著性门控。

### 从用户自己的思考中捕获什么#

原始思考是最有价值的信号。捕获精确措辞 —— 用户的
语言就是见解。不要释义。

- 新颖的观察或论点
- 框架、心智模型、启发式
- 其他人错过的想法之间的连接
- 带有推理的逆向立场
- 对外部刺激的强烈反应（什么触发了它以及为什么）

## 媒体工作流#

用户遇到的内容应该被捕获到大脑中。按主要
主题归档，而不是按格式（参见 `skills/_brain-filing-rules.md`）。

### 文章和网络内容#

**输入：** 用户共享的 URL，或对话中提到的文章。

**过程：**
1. 获取内容（`web_fetch` 或等效物）
2. 提取：标题、作者、发布、全文
3. 总结：执行摘要 + 关键论点（不是重新哈希）
4. 提取实体：提到的人员、公司、概念
5. **保存原始来源** 用于来源保留（参见下面的原始来源保留）
6. 为用户分析：不要只是总结。考虑到你
   对他们了解什么，什么是有趣的？
   标记连接、矛盾、内容机会。
7. **写入：** 根据归档规则（关于人员 -> `people/`，
   关于公司 -> `companies/`，可重用框架 -> `concepts/`，原始数据 -> `sources/`）

### 视频和播客#

**输入：** URL（YouTube、播客等）或本地音频/视频文件。

**过程：**
1. 获取记录 —— 如果可能的话使用说话者分离的（像 Diarize.io 这样的服务提供
   说话者标记的、词级时序）
2. **保存原始记录**（JSON 和人工可读的 TXT）
3. 分析：执行摘要、关键想法、带有说话者归属的关键引用、
   显著的故事/轶事、提到的人员和公司
4. 提取并交叉引用所有提到的实体
5. **硬性规则：** 每个视频/播客大脑页面必须链接到原始分离的
   记录。没有记录链接的页面是不完整的。

**写入：** `media/videos/` 或 `media/podcasts/` 带有到所有实体的反向链接。

**质量栏：**
- 引人注目的标题（不是"此视频讨论..."）
- 执行摘要使你想要观看/收听
- 作为实际见解的关键想法，不是主题标签
- 带有真实说话者姓名的逐字引用（不是"speaker_0"）
- 提取的所有实体带有上下文和反向链接

### PDF 和文档#

**输入：** 文件路径或 URL。

**过程：**
1. 提取文本（如果需要，对扫描的 PDF 使用 OCR）
2. **保存原始来源** 用于来源保留
3. 总结：执行摘要 + 关键部分 + 显著数据
4. 提取实体
5. 从实体页面交叉引用

**写入：** 根据归档规则（按主要主题归档，而不是格式）。

### 截图和图像#

**输入：** 图像文件。

**过程：**
1. 分析内容（对文本重的图像使用 OCR，对照片使用描述）
2. 如果是推文截图：提取文本、作者、日期，路由到社交媒体工作流
3. 如果是文章截图：提取文本，路由到文章工作流
4. 如果是数据/图表：提取数据点，描述发现

**写入：** 取决于内容 —— 路由到上面的适当工作流。

### 会议记录#

**输入：** 来自会议录制服务的记录，或手动笔记。

**过程：**
1. 拉取完整记录（来源真相 —— AI 摘要是中等-低信任）
2. **保存原始记录** 用于来源保留
3. 用高于线的分析、低于线的原始记录写入会议页面
4. **实体传播（强制性）：** 对于每个与会者和讨论的公司：
   - 如果新信息浮出水面，更新他们的大脑页面状态部分
   - 用链接到会议页面的内容附加到他们的时间线
   - 如果人员/公司显著并且还没有页面，创建页面
5. 会议在直到所有实体页面更新后才被视为完全摄取。

**写入：** `meetings/YYYY-MM-DD-short-description.md`

**什么使好的会议页面：**
- 揭示真正的症结，不是项目转储
- 连接到现有大脑页面（人员、公司、交易）
- 标记什么改变了（状态、决策、新信息）
- 命名张力或什么未被说出
- 捕获实际动态，不是表演性摘要

## 原始来源保留#

每个摄取的项目都必须有其原始来源保留用于来源保留。

**对 `< 100 MB 文本/PDF 使用 `gbrain files upload-raw`：** 留在 git 中（大脑仓库 `.raw/` 侧车目录）

**对 `>= 100 MB 或媒体`（视频、音频、图像）使用：** 上传到云存储
通过 TUS 可恢复上传，在大脑仓库中留下 `.redirect.yaml` 指针。

`.redirect.yaml` 指针格式：
```yaml
target: supabase://brain-files/page-slug/filename.mp4
bucket: brain-files
storage_path: page-slug/filename.mp4
size: 524288000
size_human: 500 MB
hash: sha256:abc123...
mime: video/mp4
uploaded: 2026-04-11T...
type: transcript
```

**访问存储的文件：**
- `gbrain files signed-url <storage-path>` —— 生成 1 小时签名 URL 用于查看/共享
- `gbrain files restore <dir>` —— 从云存储下载回本地

使用 gbrain 中的 `put_raw_data` 存储原始 API 响应和元数据（JSON，不是二进制）。

## 批量前测试#

处理多个项目（批量视频摄取、批量会议处理等）时：

1. **首先在 3-5 个项目上测试。** 在可用的情况下在测试模式下运行。
2. **读取实际输出。** 质量好吗？标题引人注目吗（不是
   "此视频讨论..."）？提取的实体并反向链接了吗？是
   格式干净吗？
3. **修复方法中的问题**，不是通过一次性补丁。
4. **然后才：** 用节流、每 5-10 个项目提交的批量执行。

首先测试 3 个项目的边际成本接近零。清理
100 个坏页面的成本是巨大的。

## 质量规则#

- 编译真相中的执行摘要必须被更新，不仅仅是附加时间线
- 状态部分被重写，带有每次更新的当前最佳理解。仅当前最佳理解。
- 时间线条目是 reverse-chronological（最新的优先）
- 每个提到的人员/公司如果显著都会获得页面（参见归档规则）
- 链接类型：knows、works_at、invested_in、founded、met_at、discussed
- 来源归属：每个时间线条目都包含 `[来源: ...]` 引用
- 反向链接：每个实体提及都会创建反向链接（铁律）
- 归档：按主要主题归档，而不是格式或来源（参见归档规则）

## 反模式#

- **附加到状态部分。** 状态在每次更新时用当前最佳理解重写。仅附加的状态部分变得过时和矛盾。
- **在没有反向链接的情况下摄取。** 未链接的提及是损坏的大脑。每个提到的实体都必须有从他们的页面到提到他们的页面的反向链接。
- **跳过原始来源保留。** 每个摄取的项目都必须保留其原始来源。没有来源保留的大脑页面是无法验证的。
- **在没有样本测试的情况下进行批量处理。** 首先在 3-5 个项目上测试。通过方法修复质量问题，不是通过一次性补丁。
- **释义用户的原始思考。** 用户的精确语言就是见解。捕获想法的精确措辞、论点以及框架。

## 输出格式#

```
摄取：{标题}
==================

页面：{slug}
类型：[人员 / 公司 / 会议 / 媒体 / 概念]
来源：{来源描述}

检测到的实体：N
- {实体} -> {创建 / 更新}（{slug}）

创建的反向链接：N
时间线条目：N
原始来源：{保留在路径 / 上传到云}
```

## 工具使用#

- 从 gbrain 读取页面（get_page）
- 在 gbrain 中存储/更新页面（put_page）
- 在 gbrain 中添加时间线条目（add_timeline_entry）
- 按类型在 gbrain 中列出页面（list_pages）
- 在 gbrain 中存储原始数据（put_raw_data）
- 从 gbrain 检索原始数据（get_raw_data）
- 在 gbrain 中链接实体（add_link）
- 检查 gbrain 中的反向链接（get_backlinks）
