# 数据研究

结构化研究管道：搜索来源、提取结构化数据、
归档原始数据、去重、更新规范跟踪器、反向链接实体。

## 合约

用于任何电子邮件到结构化数据管道的单一技能。跟踪投资者更新、
支出和公司指标之间的唯一区别
是**搜索查询**、**提取模式**和**跟踪器页面格式**。
所有三个都使用相同的 7 阶段管道和参数化配方。

## 何时使用

- 用户想要跟踪来自电子邮件、网络或 API 来源的结构化数据
- 用户说"research"、"track"、"extract from email"、"build a tracker"
- 用户提到投资者更新、捐赠、公司指标、文件
- 用户想要设置重复数据收集（带有定时配方）

## 阶段

### 阶段1：定义研究配方

询问用户他们想要跟踪什么。要么：
- 选择内置配方：investor-updates、expense-tracker、company-updates
- 定义自定义配方，带有：源查询、分类规则、提取模式、
  跟踪器页面路径、跟踪器格式

配方是 `~/.gbrain/recipes/{name}.yaml` 的 YAML 文件。使用 `gbrain research init`
来搭建新的配方。

### 阶段2：搜索来源

首先检查大脑（也许我们已经有此数据）。然后：
- **电子邮件** 通过凭证网关：窗口查询（每季度、每月如果截断）
- **网络** 通过搜索：公共文件、新闻稿、监管数据
- **API**：配方定义的任何结构化数据来源
- **附件**：PDF 提取、HTML 剥离

### 阶段3：分类

首先确定（来自配方的正则表达式模式），LLM 回退。
记录每个 LLM 回退以供将来正则表达式改进（失败-改进循环）。
根据配方的分类规则跳过营销、新闻通讯、噪音。

### 阶段4：提取结构化数据

**提取完整性规则：**
1. 立即保存原始源（在任何提取之前）
2. 首先使用确定性正则表达式提取字段，LLM 回退
3. 总结批次结果时：**从保存的文件中重新读取**
4. 批次处理后永远不要信任 LLM 工作记忆

这防止了已知的幻觉 bug，其中批次处理的数量从 LLM 工作记忆中
13/13 错误，而保存的文件是正确的。

### 阶段5：归档原始来源

- 用于电子邮件正文、API 响应的 `put_raw_data`
- 用于 PDF 附件、文档的 `file_upload`
- 在存储中为大型文件创建 `.redirect.yaml` 指针
- 每个跟踪器条目必须链接回其原始来源

### 阶段6：去重

在添加到跟踪器之前：
- 精确匹配（相同关键字段）→ 跳过
- 模糊匹配（相同实体 + 日期 + 容忍范围内的相似数量）→ 标记以供审查
- 相同实体+日期的不同数量 → 附加说明添加（可能是更正）

### 阶段7：更新规范跟踪器 + 反向链接

- 解析现有跟踪器页面（markdown 表格）
- 以正确部分（按年份/季度/实体分组）附加新条目
- 计算运行总计
- 反向链接每个提到的实体（人员 → people/ 页面，公司 → companies/ 页面）
- 对实体页面使用丰富服务

## 内置配方

GBrain 附带三个示例配方（参见 `~/.gbrain/recipes/`）：

1. **investor-updates** — 从投资者更新电子邮件中提取 MRR、ARR、增长、消耗、跑道、人员数
2. **expense-tracker** — 从收据电子邮件中提取金额、收件人、平台（订阅、服务、循环费用）
3. **company-updates** — 从投资组合公司更新电子邮件中提取收入、用户、关键指标

## 反模式

- 批次处理后信任 LLM 工作记忆的数量（使用提取完整性规则）
- 创建没有原始来源链接的跟踪器条目
- 在没有去重的情况下运行（导致重复计算的条目）
- 在管道代码中硬编码特定于来源的模式（使用配方）

## 输出格式

在配方的 `tracker_page` 路径处的带有 markdown 表格的大脑页面：

```markdown
### 2026

| 日期 | 公司 | MRR | ARR | 增长 | 状态 |
|------|---------|-----|-----|--------|--------|
| 2026-04-01 | 示例公司 | $188K | $2.3M | +14.7% MoM | [来源](链接) |
```

每个条目都链接到其原始来源。每个部分底部的运行总计。
