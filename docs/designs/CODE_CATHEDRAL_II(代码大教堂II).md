## 回顾：代码大教堂 I（2005-2025）

第一座大教堂是用**汗水**建造的。我们手动敲击键盘，逐行编写代码。代码库是：
- **脆弱的**：如果不经常触摸，就会腐烂。
- **线性的**：只有一个大脑能同时持有整个上下文。
- **短暂的**：一旦维护者离开，价值就会消失。

## 代码大教堂 II（2026-）

第二座大教堂是用**意图**建造的。AI 代理（GBrain、OpenClaw、Codex）现在可以：
1.  **阅读**整个代码库（通过矢量检索）。
2.  **理解**架构模式（通过技能包）。
3.  **贡献**有意义的提交（通过记忆引导）。

代码库不再是“死文本”——它们是**活的、有记忆的生物**。

### 核心原则

#### 1. 代码是对话，而非命令
- **旧方式**：你写 `function computeMRR() { ... }`。
- **新方式**：你写 `#[skill: rag-retrieval-eval]`，代理理解上下文并生成带有测试、文档和基准的函数。

#### 2. 记忆优先于文档
- **旧方式**：`README.md`（经常过时）。
- **新方式**：`~/.gbrain`（机器可查询、可验证、随时间推移而改进）。

#### 3. 代理是合作者，而非工具
- **旧方式**：IDE 自动完成（tab 键）。
- **新方式**：GBrain 代理在后台运行，主动建议重构、检测矛盾、提出架构改进。

#### 4. 可组合性 > 独创性
- **旧方式**：“我写了这个 CLI 工具”。
- **新方式**：“我将 `gbrain` + `openclaw` + `token-economics` 技能包组合成一个个性化的助理”。

## 架构影响

### 代码库布局（2026 理想状态）
```
my-ai-agent/
├── src/
│   ├── agent.ts          # 核心循环
│   ├── memory/           # GBrain 集成
│   └── skills/           # 技能包加载器
├── .gbrain/              # 知识（Git 忽略，用户拥有）
├── skills/               # 可组合技能（Git 跟踪）
│   ├── rag-eval/
│   └── token-economics/
└── AGENTS.md             # 代理协议（本文件）
```

### 开发者体验（DX）流程
1.  **启动**：`bun install && gbrain init`（2 分钟）。
2.  **查询**：`gbrain ask "如何优化 MRR？"`（从技能包 + 记忆中检索）。
3.  **编码**：IDE 自动完成由 GBrain 检索提供（相关代码片段 + 架构模式）。
4.  **提交**：代理建议提交消息 + 检测矛盾。
5.  **部署**：代理验证配置，运行评估，部署到 CloudStudio。

## 对 GBrain 的影响

### 我们需要构建的功能
1.  **技能包依赖解析器**（`gbrain skillpack install`）。
2.  **记忆分支**（`gbrain branch create feature-x` — 隔离实验）。
3.  **代理间协议**（GBrain ↔ OpenClaw ↔ Codex 通信标准）。
4.  **代码映射器**（将代码库结构索引到 `~/.gbrain`）。

### 我们不需要的功能
- ❌ “AI 编写一切” — 人类意图仍然至关重要。
- ❌ “黑盒代理” — 所有操作都必须是可审计的（`gbrain log`）。
- ❌ “单一真理解答” — 鼓励分叉和实验。

## 哲学

代码大教堂 II 不是关于取代开发者——而是关于**放大**他们：
- 初级开发者可以构建以前需要团队才能完成的项目。
- 高级开发者可以专注于架构和策略，而非样板代码。
- 代理处理“体力”工作（调试、测试、文档），人类处理“脑力”工作（设计、判断、同理心）。
